# 화면 인식 — 캡처에서 자리 판단까지

펫이 글자 위에 앉지 않으려면 화면이 어디가 비었는지 알아야 한다. 그 답은 **한 화면을 64칸
폭으로 축소한 휘도 격자**(`LuminanceField`)에서 나오고, 격자를 만드는 캡처는 셸이, 격자를
읽어 "비었는가"를 판정하는 것은 코어가 한다. 이 문서는 그 경로가 지금 어떻게 생겼는지, 그리고
2026-09-15에 그것이 두 시간 넘게 끊겨 있었던 일의 진단과 수정이다.

## 1. 경로

```
코어가 요청   pet_runtime.rs  request_luminance()             3초(활동 중) · 6초(배회·휴식)마다
     ↓        ActivityEffect / PetOutput.luminance_requests
셸이 캡처     RoamlingRuntime.swift  requestLuminanceRefresh()  권한 · 스로틀 · 진행 중 검사
     ↓        MacCaptureProvider.captureLuminanceField()       SCShareableContent → SCScreenshotManager
셸이 캐시     RoamlingRuntime.cachedLuminance                  한 칸. 화면이 셋이어도 한 칸
     ↓        judgeableLuminance → PetInput.luminance
코어가 판정   placement.rs · clearance.rs · emptiness.rs        필드 없으면 "모름"
```

**필드가 없으면 코어는 글자를 못 본다.** 세 자리가 그렇다:

- 앉아 있는 동안 글자가 깔렸는지 보는 검사가 필드 없이는 그대로 돌아간다 —
  `placement.rs`의 `let Some(field) = situation.world.luminance.as_ref() else { return self.carried.clone(); }`
- 산책 목적지를 빈 곳으로 고르는 `comfortable()`이 `None`을 돌려준다.
- 활동 중 자리를 `CoveringWork`로 떠나는 판정도 `evaluation.emptiness`가 있어야 한다.

캐럿 회피는 별개 경로(접근성)라 살아 있다. 그래서 정확한 증상은 "아무것도 못 피한다"가 아니라
**"글자를 못 피한다"**다.

**필드 범위 밖은 "모름"이다.** `emptiness.rs`가 사각형을 격자에 맞춰 자르는데, 완전히 밖이면
span이 퇴화해 `None`을 돌려준다(`last_column - first_column < 1`). 다른 화면 필드를 들고
있으면 틀린 답이 아니라 **답이 없는** 것이다 — 확인했다.

2026-09-17부터 런타임의 `ClearanceMap::distance`는 펫 몸체 전체가 필드 안에 들어와야
관측된 후보로 인정한다. 내용과 겹치는 후보를 제외하고 몸체와 내용 셀 사이 거리를 24pt
구간으로 비교한다. 배회·작업·휴식이 이 기준을 공유하며 하단 선호는 그다음이다.
휴식 도착 후와 수면 중 새 필드도 재검사한다. 선택·미관측 후보·수면 보류 규칙은
`docs/placement.md` 3.2.3과 `docs/behavior-flow.md` 3.1이 정본이다.

이 격자는 OCR이 아니다. 사진·아이콘도 내용으로 잡히며 축소 과정에서 작은 글씨를 놓칠 수 있다.
후보 중 더 멀리 떨어진 곳을 찾는 구현이며, 화면 전체에서 수학적인 최장 거리를 보장하지 않는다.

## 2. 2026-09-15의 장애 — 확정된 것과 아닌 것

**증상.** "글자 위에 계속 앉아 있다." 화면 기록 권한은 켜져 있었다(사용자 확인). 디스플레이
셋, 데스크탑 x = -1920 ~ 3648.

**진단 로그** (`/tmp/roamling-rest.log`, 범주별로 값이 **바뀔 때만** 한 줄):

```
159.9  capture authorised, none yet
160.1  capture available            ← 한 번 성공
294.7  capture authorised, none yet ← 필드가 사라짐
       (8,489초 = 2시간 21분, 변화 없음)
8783.4 capture authorised, none yet ← 다섯 범주가 같은 시각에 다시 찍힘
8783.6 capture available
```

### 확정

- **한 프로세스가 294.7부터 죽을 때까지 필드를 못 받았다.** 8783.4에 다섯 범주가 동시에
  찍힌 것은 런타임 재생성이 아니라 **새 프로세스의 첫 틱**이다 — 시계가
  `ProcessInfo.processInfo.systemUptime`(부팅 기준, 모든 프로세스 공통,
  `RoamlingRuntime.swift` 생성자)이고 진단 파일은 append라 **여러 실행이 한 파일에 쌓인다.**
  자동 업데이트가 0.6.0을 켰을 때 새 프로세스가 0.2초 만에 캡처에 성공했다. 옛 프로세스는
  **스스로 회복한 적이 없다.**
- 필드가 없으면 위 §1의 세 자리가 전부 "모름"으로 떨어진다. 증상과 일치한다.

### 미확정 — 그리고 왜 확정할 수 없었나

`294.7`의 `available → none yet` 전환은 **실제로 기록됐다.** 캐시는 `await`가 돌아온 뒤에만
덮어쓰므로(`cachedLuminance = field`), 호출이 영원히 멈췄다면 로그는 계속 `available`이어야
한다. 그러니 **최소 한 번은 nil을 돌려받아 캐시를 지웠다.** 그 뒤가

1. 후속 요청이 매달렸다(`luminanceTask`가 영원히 남아 이후 요청이 전부 guard에서 막힘), 또는
2. 요청은 계속 완료되는데 매번 nil이었다

인지는 **같은 로그를 만든다.** `MacCaptureProvider`가 content 조회 실패 · 대상 display 미발견 ·
screenshot 실패 · 변환 실패를 전부 `try?`로 삼켜 하나의 nil로 합치기 때문이다. 재실행이
낫게 한 것도 두 경우를 가르지 못한다 — Task뿐 아니라 프로세스 안의 SCK 상태도 같이 초기화된다.

**"응답을 멈췄다"는 가설이고, "유효한 필드를 못 받았다"까지가 사실이다.** 두 번째 의견
(gpt-6-astra)이 이 구분을 짚었고 맞다.

### 배제한 것

- **스로틀 산술.** `luminanceCapturedAt`은 이름과 달리 *시도* 시각이고, 같은 시계로 3·6초를
  비교한다. 실패가 완료되기만 하면 수 시간 재시도를 막을 이유가 없다.
- **`?? nearestDisplay`.** 영구 정지의 원인은 아니다. 다만 고른 display id가 SCK 목록에 없으면
  매번 nil이므로 **그 실패는 따로 이름이 있어야 한다** (§3 ①).
- **MainActor가 막힘.** 그 시간 내내 다른 범주는 계속 기록됐다.
- **화면 셋이라 자주 틀린 화면을 찍는다.** 배회 요청은 펫이 선 화면을 겨냥한다
  (`request_luminance_for_roaming`). 그리고 틀린 화면 필드라도 있으면 로그는 `available`이라
  이번 장애의 설명이 못 된다. 미입증이고, 이번 변경 범위 밖(§4).

## 3. 수정 — 셋, 이 순서로 (사용자 승인 2026-09-15)

### ① 실패를 보이게 한다

`CaptureProviding.captureLuminanceField`가 `LuminanceField?` 대신 **`CaptureOutcome`**을
돌려준다 — 성공이면 필드, 실패면 **어느 단계가 왜**:

| 실패 | 뜻 |
|---|---|
| `noContent` | `SCShareableContent` 조회가 던짐 |
| `displayNotFound` | 조회는 됐는데 그 display id가 목록에 없음 — `?? nearestDisplay`가 고른 화면을 SCK가 모를 때 |
| `noImage` | `SCScreenshotManager`가 던짐 |
| `unusableImage` | 이미지는 왔는데 격자로 못 바꿈 |
| `cancelled` | 단계 사이에서 취소를 봄 |

셸은 그 결과를 **`capture-request` 범주**에 적는다: `ok` · `failed: <reason>` ·
`timed out (<stage>)` · `late completion ignored`. **Rust가 매 틱 내는 `capture` 범주(캐시
상태)와 분리한다** — 같은 범주에 쓰면 다음 틱의 `available`과 번갈아 찍혀 change-only 기록이
무너진다. 메시지에 경과 시간·요청 번호 같은 매번 다른 숫자를 넣지 않는다.

**`launch` 줄을 시작할 때 하나 적는다** — pid와 버전. append 파일에서 실행 경계가 보이게.
이번에 그게 없어서 두 프로세스의 기록을 하나의 타임라인으로 한 시간을 잘못 읽었다.
**파일에만 적고 메모리 버퍼에는 넣지 않는다** — 프로세스 경계는 한 프로세스짜리 버퍼에 뜻이
없고, 버퍼에 넣으면 첫 항목이 돼서 표시되는 모든 시각의 기준(`DiagnosticsLog.text`)을 밀어
녹화 트레이스가 0.1초씩 어긋났다.

**"버렸다"는 버린 것이 있을 때만 적는다.** 화면 배치가 바뀌거나 멈출 때 요청도 필드도 없었으면
줄을 남기지 않는다 — 캡처를 끈 녹화 세션의 화면 변경이 아니면 `dropped`가 생긴다.

### ③ 매달린 요청에 시한을 둔다 — `cancel()`은 시한이 아니다

Swift 취소는 협력적이라 SCK 호출은 안 멈춘다. `withTaskGroup` + `cancelAll()`도 자식이 안
끝나면 그룹이 안 돌아온다. 그래서 시한은 **기다리기를 그만두는 것**이지 호출을 멈추는 것이 아니다.

- **틱에서 시계로 판정한다.** `luminanceTask`가 있고 `now - luminanceStartedAt >= 5초`면
  요청을 논리적으로 만료한다: 세대 번호를 올리고, 슬롯을 비우고, `capture-request timed out
  (<stage>)`를 적는다. `Task.sleep`을 쓰지 않는다 — 실시간이라 가짜 시계 테스트가 안 되고,
  취소 경쟁이 하나 더 생긴다. 틱이 최소 0.5초마다 도니 해상도는 충분하다.
- **세대 번호가 소유권이다.** 요청마다 번호를 받고, 완료 시 **자기 번호가 현재일 때만** 캐시와
  슬롯을 만진다. A가 만료된 뒤 B가 시작되고 나서 A가 돌아오면, A는 B의 슬롯을 비우거나 B의
  필드를 덮지 못한다 — `late completion ignored` 한 줄만 남긴다. 만료·정상 완료·`stop()`·
  화면 변경 전부 같은 검사를 거친다.
- **provider는 단계 사이에서 취소를 본다.** 만료된 content 조회가 늦게 돌아와 screenshot까지
  시작하지 않게.
- **연속 만료에는 backoff.** 만료가 이어지면 다음 시도 간격을 두 배씩(상한 60초) 늘린다.
  포기한 호출이 OS 안에서 아직 돌고 있을 수 있어서, 3~6초마다 무제한으로 새로 쌓지 않는다.
  성공하면 0으로 돌아온다. **논리적 회복과 OS 작업의 실제 종료는 별개다.**

### ② 실패가 캐시를 지우지 않게 한다 — 단, 기한이 있다

수정 전에는 실패 한 번이 직전의 멀쩡한 필드를 nil로 덮었다. 그러나 **무기한 보존은 더 나쁘다.**
`LuminanceField`에 시각이 없고 소비 쪽에 나이 검사가 없어서, 두 시간 전 화면을 지금 화면처럼
쓰게 된다. 배치는 필드가 *있으면* 본 것으로 치고(`saw_capture`), 옛 필드가 지금 글자 자리를
"비었다"고 하면 거기 앉는다 — **`None`보다 나쁜 결정이 실제로 가능하다.**

- **마지막 시도 시각과 마지막 성공 시각을 따로 든다.**
- 코어에 넘기는 것은 **마지막 성공이 12초 안**일 때만이다. 지나면 보관 여부와 무관하게 `None`.
  12초는 갱신 주기(3~6초)의 두 배쯤이고, 검증할 정책값이지 증명된 안전 한계가 아니다.
- **화면 배치가 바뀌면 캐시를 버린다.** `handleDisplayChange`는 좌표계와 world를 바꾸면서
  진행 중 요청과 캐시도 무효화한다. 권한이 빠져도 필드를 사용하지 않는다(`judgeableLuminance`).

## 4. 이번에 안 하는 것

**화면별 캐시.** 한 칸이라 펫이 다른 화면으로 가면 그 사이 "모름"이 되는 것은 맞다. 그러나
(a) 이번 장애의 원인이 아니고, (b) 코어가 필드 하나만 받으므로 "지금 선 화면과 목적지 화면이
다를 때 어느 필드를 주는가"를 먼저 정해야 하며, (c) 그건 배치 동작을 바꾸는 일이라 따로
게이트를 지나야 한다. 실사용에서 다시 보이면 그때다.

## 5. 검증

기존 fake(`FakeCaptureProvider`)는 즉시 돌아오고 녹화 트레이스는 캡처를 끈다. **그러므로 기존
테스트 초록은 시한의 안전성을 아무것도 증명하지 않는다.** 하네스에 직접 넣는 것:

- 취소를 무시하고 안 돌아오는 호출이 다음 요청을 막지 않는다
- A 만료 → B 성공 → A 늦게 도착: 현재 필드는 B의 것이고 슬롯은 안 비워진다
- 실패가 이어져도 12초 안에는 직전 필드로 판정하고, 지나면 `None`
- 실패 사유가 바뀔 때만 한 줄씩 남는다 (같은 실패가 매 틱 쌓이지 않는다)

`RuntimeTrace.txt`는 캡처가 꺼진 세션이라 바이트 불변이어야 한다. 바뀌면 그건 이 변경이
캡처 밖으로 샜다는 뜻이다.
