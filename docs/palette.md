# 색 팔레트 — 내 고양이 만들기 (R1)

**상태: 설계 끝, 코드는 아직 없다.** 요청 원문과 맥락은 `docs/requests.md` R1.

**세 단계로 간다 (사용자 결정 2026-09-12).**

| | 무엇 | 왜 그 순서인가 |
|---|---|---|
| **0** | **디버그 빌드 전용 실험 창** | 색을 돌려 가며 **눈으로 본다.** 엔진이 예쁜 색을 내는지 모르는 채로 메뉴 줄부터 만드는 것은 거꾸로다 |
| 1 | 프리셋 둘 — 검은 모치 · 무작위 모치 | 0에서 고른 값이 그대로 프리셋이 된다 |
| 2 | 색 직접 고르기 | 1이 실물에서 좋다는 것이 확인된 뒤 |

**0단계는 걷어낼 수 있는 물건이다.** 릴리스 빌드에 들어가지 않고, 1단계가 서면 지워도 된다.
사용자의 말 그대로 — "나중에 걷어내더라도, 디버그 빌드에서만 보이는 창".

**R4(검은 고양이)가 1단계 프리셋으로 같이 풀린다** — 새 시트를 그릴 필요가 없다.

## 1. 왜 런타임 리컬러인가 (사용자 결정 2026-09-12)

두 갈래가 있었다 — 런타임에 픽셀을 옮기거나, 시트를 미리 여러 벌 굽거나. **원문이 갈래를
정한다:**

> "**색상 팔레트를 내가 맘대로 조정해서** 원하는 고양이를 만드는 기능이 있었으면 좋겠다고
> 했어. 막 **무지개색** 고양이? 이러면서 장난치기도 했어."

미리 구운 시트 몇 벌은 고정된 선택지다. "맘대로"도 "무지개색"도 구조적으로 나오지 않는다.
그래서 런타임이다. **`PetImage`(RGBA8) 위의 바이트 변환이므로 공유 Rust 한 벌이고 양 플랫폼이
공짜로 따라온다.**

## 2. 알고리즘 — 이미 있다

`scripts/unify_palette.py`는 도구가 아니라 **검증된 방법론**이다. 행마다 색이 드리프트하던
문제를 풀면서 만들어졌고, 우리가 필요한 변환이 그대로 들어 있다.

**가족은 명도(HLS의 L) 밴드다.** 코드의 `FAMILIES` 기준:

| 가족 | 명도 | |
|---|---|---|
| (검정) | < 10 | 외곽선. **고정한다** |
| `dark` | 10 – 40 | |
| `orange` | 42 – 58 | |
| `cream` | 82 – 100.1 | |

**밴드 사이의 간격은 의도적이다.** 경계를 그라디언트 한가운데 그으면 행마다 다른 혼합(진짜 색
+ 안티에일리어싱 가장자리)이 잡혀 **같은 가족이 두 번 같지 않다.** 간격에 빠진 픽셀은 버려지지
않고, 아래의 "가장 가까운 앵커" 규칙이 가져간다.

**앵커는 버킷의 무리 중심이다.** 색을 8로 나눠 버킷을 세고, 최다 버킷을 고른 뒤 **그 안에서
가중 평균**한다. 손실 WebP가 평평한 크림을 한두 레벨씩 흩어 놓기 때문에 최빈색 하나를 집으면
그 구름의 임의 구성원이 잡힌다.

**적용은 밴드가 아니라 거리로 한다.** 각 픽셀은 **RGB 거리로 가장 가까운 앵커**의 델타를
받는다. 후보 목록에 `(0,0,0)` 검정이 델타 0으로 함께 들어가므로 외곽선이 저절로 붙잡힌다.
안티에일리어싱 픽셀은 실제로 섞인 쪽을 따라간다.

**평행이동이라 음영이 산다.** 각 픽셀의 "앵커로부터의 거리"가 보존되고 가족의 위치만 옮겨지니
하이라이트·그림자·부드러운 가장자리가 그대로다. 알파는 건드리지 않는다 — 리컬러이지 실루엣은
우리 것이 아니다.

### 달라지는 것

`unify_palette`는 **행들의 중앙값**으로 모은다. 우리는 **사용자가 고른 색**으로 옮긴다.
`delta = 사용자_목표 − 앵커` 한 줄만 바뀌고 나머지는 같다. 중앙값·행 밴드 분할·deadzone
(도구의 멱등성 장치)은 런타임에 필요 없다.

## 3. 어디에 거는가 — 그리고 먼저 밟을 함정

`rust/roamling-core/src/pet_image.rs`의 `PetImage`가 그 자리다. 주석이 스스로 말한다 —
"결정하지 않는다. 바이트 변환이고, 그래서 이식 가능하다."

**`decode`가 알파를 프리멀티플라이한다.** 그 뒤에 색을 옮기면 **부드러운 가장자리가 전부
틀어진다.** 리컬러는 **곱하기 전 straight alpha에서** 돌아야 한다. 인구조사가 알파 ≤ 200을
빼는 것도 straight alpha를 전제한 규칙이다. 같은 파일이 기록한 47,678픽셀 반올림 사건과 같은
계열의 함정이다.

`PetImage::decode` 호출부는 넷이다 — `roamling-pet/src/package.rs:325`(설치된 패키지),
`roamling-pet/src/lib.rs:136`·`:183`(내장 표준·확장 시트), `roamling-core/src/ffi.rs:1992`
(macOS가 쓰는 uniffi 입구). **네 곳이 같은 변환을 거치게 해야 한다** — 한 곳만 빠지면 내장
고양이와 설치한 고양이의 색이 갈린다.

시트 사실은 `docs/art/mochi-sheet.md`: 표준 8×9(1536×1872), 확장 8×3(1536×624), 셀 192×208.
**시트가 둘이므로 앵커도 둘에서 재거나 합쳐서 재야 한다** — 따로 재면 두 시트의 색이 갈린다.

## 4. 어떻게 고르나 — 창을 만들지 않는다 (사용자 결정 2026-09-12)

**색 고르는 화면을 새로 만들지 않는다.** 이미 있는 메뉴 트리에 한 단계를 더한다:

```text
펫 ▸ → Mochi ▸ → 색 고르기
                   기본 (선택됨)
                   검은 모치
                   무지개 모치
                   무작위 모치
                   색 직접 고르기…   ← 나중
```

이게 원래 잡았던 "양 플랫폼에 창 하나씩"을 통째로 없앤다. 메뉴는 macOS `ShellMenu`와 Windows
`tray.rs`가 이미 같은 모양을 들고 있으므로 줄만 는다.

**첫 판은 검은 모치와 무작위 모치 둘이다 (사용자 결정).** 색을 직접 고르는 화면 없이 **리컬러
엔진이 실물에서 도는지를 먼저 본다.** 팔레트 UI는 엔진이 맞다는 것이 확인된 뒤의 일이다.

**R4가 여기서 같이 풀린다.** "검은색 고양이 한 마리 더"는 프리셋 하나이고, **새 시트를 그릴
필요가 없다.** 아내분이 R1을 R4보다 먼저라고 한 것이 결과적으로 맞았다.

**적용 범위는 내장 Mochi뿐이다 (사용자 결정).** 앵커 값을 우리가 알고 있어 실패할 일이 없고,
남의 펫을 제작자 의도와 다르게 보이게 만들지 않는다. 그래서 `펫 ▸` 안에서도 Mochi 아래에만
붙는다 — 설치된 패키지는 지금처럼 평평한 줄로 남는다.

### 정해진 것

- **무작위는 고를 때 한 번 뽑고 고정한다 (사용자 결정 2026-09-12).** 그 뒤로는 그 고양이가
  내 고양이로 남는다. 다시 누르면 새로 뽑는다. **뽑은 색을 설정에 같이 저장해야** 이 규칙이
  성립한다. 실행 전에 "이 색으로 할까요" 확인 창을 두자는 이야기가 있었고, 그건 1단계에서
  다시 본다.
- **앵커는 빌드 때 재어 상수로 박는다.** 내장 Mochi만 대상이므로 시트가 고정이고, 런타임
  측정 비용이 0이 된다. 재는 것은 `unify_palette.py`가 이미 하는 일이다.
- **색은 `BuiltInPetKind`의 case가 아니다.** 그 열거형은 `mochi` · `fatMochi` 둘뿐이고
  `roamling.builtInPet`에 문자열로 저장된다(`MascotPetFactory.swift:6`). **색은 펫 종류가
  아니라 별도 축**이므로 case를 늘리지 않는다 — 늘리면 종류 × 색으로 조합이 터진다.

### 0단계 — 디버그 창은 `tuning.rs`를 본뜬다

새로 발명할 것이 없다. `rust/roamling-win/src/tuning.rs`가 같은 모양의 실물 선례다:

- `RegisterClassW`로 자기 클래스, `WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU`
- `InitCommonControlsEx(ICC_BAR_CLASSES)` — **이걸 안 부르면 트랙바 생성이 전부 실패한다**
- thread-local 슬롯에 창을 들고, 닫을 때 파괴가 아니라 `SW_HIDE`
- **띄우지 않고 만들기만 하는 `create()`가 따로 있어 테스트가 레이아웃을 검사한다.** 같은
  구조를 따르면 창 테스트가 공짜로 따라온다

**Windows에만 만든다.** 지금 실기 테스트가 Windows이고, 이 기계에서 컴파일되지 않는 macOS
창을 같이 쓰면 검증 못 하는 코드가 두 벌이 된다 — 이번 세션에 그 이유로 CI가 두 번 빨갛게
됐다. 걷어낼 실험 창이라면 더더욱 한쪽만.

**릴리스 빌드에는 들어가지 않는다.** 모듈 전체를 `#[cfg(debug_assertions)]`로 감싼다. 저장소의
디버그 분기 관례는 `main.rs:7`의 `#![cfg_attr(not(debug_assertions), ...)]` 하나뿐이고, 같은
결이다.

### 아직 정하지 않은 것

1. **`Mochi`가 지금은 체크되는 줄인데 하위 메뉴가 되면 "Mochi를 고른다"가 어디로 가나.**
   색 하나를 고르는 것이 곧 Mochi 선택이 되게 하면 줄이 늘지 않는다. 설치된 패키지는 평평한
   줄로 남으므로 그 목록만 모양이 갈린다. **1단계에서 정한다.**
2. **0단계 창이 무엇을 조작하게 할 것인가** — 가족 셋(`dark` · `orange` · `cream`)의 목표색을
   각각 RGB 슬라이더로? 아니면 색상(hue) 하나를 돌리면 셋이 같이 움직이게? 전자가 정확하고
   후자가 "무지개색 고양이"에 가깝다. **만들면서 정해도 되는 것**이라 여기서 막지 않는다.

## 5. 검증

- **원본과 결과의 알파가 한 바이트도 다르지 않아야 한다.** 실루엣을 안 건드린다는 규칙이
  코드에서 지켜졌는지는 그것으로만 확인된다.
- **델타가 0이면 바이트가 그대로여야 한다.** 항등이 항등이 아니면 어딘가에서 반올림이 새고
  있다는 뜻이다.
- **프리멀티플라이 전에 걸렸는지** — 반투명 가장자리 픽셀을 골라 값을 손으로 확인한다.
  이 함정은 눈으로 보면 "조금 지저분하다" 정도로만 보인다.
- `RuntimeTrace.txt`와 differential 픽스처는 **바뀌면 안 된다.** 색은 펫의 판단에 닿지 않는다.
- 프레임 해시(`PreW2FrameHashes.swift`)는 기본 팔레트에서 **그대로여야 한다.**

**Swift는 이 기계에서 컴파일되지 않는다.** macOS 쪽은 `gh workflow run check-macos.yml`이
유일한 검증 통로다(2026-09-12에 두 번 그것으로 잡았다). Windows는 `.\scripts\test.ps1`.
